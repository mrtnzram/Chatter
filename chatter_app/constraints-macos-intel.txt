# pip constraints for the Intel (x86_64) macOS build ONLY.
#
# Purpose: keep the frozen app's minimum macOS version at 10.13 (High Sierra),
# because Intel Macs in the lab run old macOS and the loader refuses to start
# an app whose binaries demand a newer OS ("the application cannot be opened").
#
# Every pin below is the newest release whose macOS x86_64 wheel still targets
# 10.13 or lower. Bumping any of them WILL raise the app's minimum macOS and
# lock out those machines. The "Verify macOS deployment floor" step in
# .github/workflows/release.yml fails the build if that happens, so this file
# and that check are meant to be read together.
#
# Wheel platform tags at the time of writing (cp311, x86_64):
#   kivy     2.2.1  -> see note 3 below (the wheel tag is NOT the whole story)
#   numba    0.60.0 -> macosx_10_9      (0.61 -> 10_14, 0.62 -> 10_15)
#   llvmlite 0.43.0 -> macosx_10_9      (0.44 -> 10_14, 0.45 -> 10_15)
#   soxr     0.4.0  -> macosx_10_9      (0.5+ -> 10_14); pulled in by librosa
#   cffi     1.17.1 -> macosx_10_9      (2.0 -> 10_13, 2.1 -> 10_15)
#   numpy    2.0.2  -> macosx_10_9      capped by numba 0.60 (needs numpy<2.1)
#   scipy    1.15.3 -> macosx_10_13     (1.16+ -> 10_14)
#
# Two further notes:
#
# 1. numba / llvmlite also stopped publishing macOS x86_64 wheels entirely in
#    later releases, so without a pin pip tries to build llvmlite from source
#    and the CI job dies. These pins solve that too.
#
# 2. numpy and scipy each publish TWO x86_64 wheels per release: a low
#    deployment-target one and a macosx_14_0 one. pip prefers the highest tag
#    the BUILD machine supports, so on the runner it silently picks the 14_0
#    wheel even with the version pinned. The workflow therefore force-downloads
#    the low-target wheels by platform tag; these version pins exist so that
#    the later `pip install -r requirements` cannot pull the 14_0 ones back in.
#
# 3. kivy vendors its own copies of SDL2 and friends inside kivy/.dylibs/,
#    as EXTENSIONLESS files named "SDL2", "SDL2_ttf", "png" and so on. Those
#    binaries carry their own deployment targets, which the wheel's platform
#    tag says nothing about: the 2.3.0 wheel is tagged macosx_10_9 but ships a
#    libpng built for macOS 12.7, pulled in because its SDL2_ttf links libpng.
#    2.2.1 does not ship libpng at all and its SDL2 family is built for 10.13.
#    This is why requirements_kivy.txt asks for kivy>=2.2.1 rather than
#    >=2.3.0 -- so this pin does not create an unsatisfiable resolution.
#    Lesson: check the vendored .dylibs, not just the wheel tag.
#
# Applied via the PIP_CONSTRAINT env var in .github/workflows/release.yml.
# Not used by the arm64 macOS or Windows builds, which get current versions.
kivy==2.2.1
numba==0.60.0
llvmlite==0.43.0
soxr==0.4.0
cffi==1.17.1
numpy==2.0.2
scipy==1.15.3
